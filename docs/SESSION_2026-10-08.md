## 1. THE HEADLINE: live frames are over-exposed, and that is the whole problem

Everything that looked like "the model is broken in WPF" came down to this.

Measured with OpenCV over six training samples
(`F:\COPPER-RELATED FILES\copper_data\sample\*.bmp`) and the live captures the
app itself saved (`bin\x64\Debug\net10.0-windows\LiveCaptures\*.png`, saved
post-ROI, i.e. exactly what inference consumed):

| | training stills | live captures |
|---|---|---|
| mean brightness | **66.6** | **200.8**  (3× brighter) |
| **% pixels clipped (≥250)** | **2.6 %** | **60.8 %** |
| % true black (≤5) | 0.47 % | **0.00 %** |
| size | 1095–1217 × 1536 | 1216 × 1536 ✓ |

**Over 60 % of every live frame is saturated to pure white.** Clipped pixels
are destroyed information — no threshold, preprocessing or retraining can
recover detail that was never recorded. PatchCore is being shown a nearly
white rectangle and correctly reports "this is nothing like my training data".

Two supporting observations:
- **The ROI crop is correct.** Live 1216×1536 vs training 1095–1217×1536 —
  composition matches. The ROI work is not the problem.
- **Zero dark pixels.** Training had 0.47 % true black (background / strip
  edges); live has none. The whole histogram shifted up and clipped — classic
  over-exposure, not a colour or lighting-angle issue.

### Most likely cause (not yet confirmed)

`CameraBridge/Program.cs` **never configures the camera**. It does
`Connect()` → `StartStreaming()` → `GetImage()` and nothing else — no
`ExposureTime`, no `Gain`. The camera therefore runs at whatever it defaults
to on connect, whereas the training images were recorded through Baumer's own
software with tuned exposure. Same camera, different capture tool, different
exposure.

### Next steps

1. Open Baumer's own viewer, read off the `ExposureTime` and `Gain` it uses —
   that is the known-good target that produced the training set.
2. Add both as settable features in the bridge (NeoAPI exposes
   `cam.f.ExposureTime` / `cam.f.Gain`), surfaced through `config.json` + UI,
   applied explicitly on connect rather than inherited.
3. Re-run the comparison above. **Target: mean ≈ 67, saturation ≈ 2.5 %.**
   Roughly a 3× exposure reduction, but gain matters too.

### How this was proven (so nobody re-litigates it)

- Same model file + same engine gave **GOOD** on an uploaded `.bmp` in WPF,
  matching the Python trainer's **GOOD** on its own sample → the WPF port and
  the ONNX model are fine.
- Every **BAD** was on a live frame.
- **Capture & Inspect** now saves the exact post-ROI pixels to PNG. Running
  that identical file back through the file path (Browse → Run Detection)
  produced **the same BAD verdict** → not a code-path bug, not the ROI crop,
  not the capture conversion. The pixels themselves are the problem.

## 3. Bugs fixed

- **NRE on Stop Stream** — pipeline's inspect callback used null-forgiving
  `_stripRecorderProbe!`; the consumer thread could hold a queued frame after
  teardown nulled it. Now null-safe, and teardown order is: stop trigger →
  `End()` pipeline → finalise recorder.
- **Stop Stream didn't stop the scan** — the interval timer kept firing, so
  captures and inference continued invisibly after the preview stopped.
- **Scan overwrote manual results** — a Run Detection result was repainted by
  the next scan segment a second later. The scan now holds off on the panels
  while the live view is inactive (it still records to MongoDB).
- **Crash opening a strip run** — `segments.ToDictionary(s => s.SegmentIndex)`
  threw on duplicate indices (`Key: 36`). Duplicates happen because the
  recorder field is read per job, so a late in-flight job lands in the *next*
  run carrying its old index. Now tolerated and surfaced in the map hint.
- **`SetArray` on a 3-channel Mat** — OpenCvSharp needs `Vec3b[]`, not a flat
  `byte[]`; replaced with a direct `Marshal.Copy` into `mat.Data`.
- **Trigger mode didn't persist** — only saved via `OnClosing`, which is
  skipped on abnormal exit. Now saved immediately on change.
- **`ScanController` speed estimate** — assumed every sample arrives at
  `Encoder.PollHz`. Interval mode arrives at a different rate, which inflated
  the predicted lead and skipped several segments per tick. Now mode-aware.
  Verified with a standalone test: fires segments 1,2,3,4,5 one per tick.

## 4. Environment traps that cost real hours — check these FIRST

1. **Two build outputs drift apart.** `bin\Debug\...` and
   `bin\x64\Debug\...` each have their own `Assets\`. A new model copied into
   source `Assets\` only reaches the output you actually rebuild. Spent an
   afternoon testing an old model this way. **Check the `_meta.json`
   timestamp in whichever `bin\...` you launch.** Also: the app caches the
   detector per session, so swapping files while it runs does nothing until
   restart.
2. **Windows Smart App Control** (`VerifiedAndReputablePolicyState = 1`,
   Evaluation) blocks freshly-built unsigned DLLs — `CameraBridge.dll` died
   with `0x800711C7` before `Main` ran, so it produced no log and looked like
   "camera won't connect". Turn it off while it is still in Evaluation; once
   it flips to On it cannot be reversed without reinstalling Windows.
3. **NuGet `packageSourceMapping` is all-or-nothing.** The user-level
   `NuGet.Config` mapped only `neoAPI`, so every other package matched no
   pattern and restore failed with `NU1100` — invisible until the global cache
   was cleared. Fixed by adding a `*` catch-all for nuget.org (most specific
   pattern still wins, so neoAPI resolves locally).
4. **C: ran to 0 GB free** → MongoDB refused to run → the scan could not open
   a StripRun → it **never armed** → no captures, no inference, empty panels,
   no banner. Looked exactly like broken inference. The Mongo data dir alone
   was 11.6 GB.
5. **`defect_detection_db` grows fast** because every report stores the same
   PNG **twice**: `ImageData` (binary) and `ResultImageBase64` (base64, +33 %).
   Neither is `[BsonIgnore]`. ~2.33× per report, at one segment/second.
   Worth dropping one field.
